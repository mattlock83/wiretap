# Wiretap product roadmap

**Direction:** make Wiretap the default API testing accelerator, turning existing
tests into shared integration knowledge and using that knowledge to find and
verify the cases teams have not written.

**Status:** proposed product and commercial direction, updated 2 October 2026. The
implementation baseline is commit `66a5fa0`. Everything under the delivery phases
is planned unless explicitly identified as available today. Phases have outcome
gates, not delivery dates; separate implementation plans should define each
release's scope.

## The product we are building

Our founding thesis is that integration assumptions are a major source of defects
and late feedback. Teams frequently develop against fakes before their dependencies
exist or can be run locally. Those fakes become an informal contract, but the
agreement between the fake, the consumer and the real provider is rarely tested
systematically.

Wiretap should make that agreement explicit and continuously test it. A team
should be able to use a dependency like a well-tested SaaS API: understand its
public contract, rely on version-specific evidence, and find incompatibilities
without learning its internals or assembling an integration environment.

The promise is: **write the important flows once; Wiretap checks the assumptions,
explores the boundaries, and shows what remains unverified.** This applies equally
to software written by people, generated by agents, or assembled from both.
Runtime evidence should stand independently of how code was produced or reviewed.

The ambition is to replace the need for separate API contract-testing,
record/replay, dependency simulation, regression-diff and exploration products in
this workflow. We win through a coherent feedback loop and easy adoption, rather
than requiring teams to assemble and interpret several disconnected tools.

The business model is an open local engine, a free public bundle registry for
open-source projects, and paid private registries for companies. Public evidence
helps teams adopt Wiretap; private shared evidence makes it valuable across an
organization. The paid service provides reliable collaboration, verification
coordination and governance while the engine remains independently useful.

This is API-boundary assurance. Distributed scheduling, real database behaviour
and infrastructure-specific failures can still require other tests. Wiretap
should make that remaining scope explicit while steadily reducing how much needs
an expensive shared environment.

## Principles that constrain the design

1. **Find assumptions before they become integration defects.** Support fake-first
   development, label its claims provisional, and give teams a path to verify
   them as soon as provider evidence or an implementation becomes available.
2. **Start with how teams already work.** Keep their languages, test frameworks,
   clients, assertions, mocks and CI. Capture remains a library integration;
   derived verification and exploration use an optional Wiretap runner.
3. **Require no Wiretap-specific application instrumentation.** Reuse standard
   tracing where available. Without propagation, use sequential execution or
   isolated workers; never guess which parallel test owns a request.
4. **Keep the core open and locally executable.** No required Wiretap account,
   hosted backend, proprietary artifact store or model provider. Publish formats,
   APIs and extension contracts so other tools can read, produce and use evidence.
5. **Remain code driven.** Configuration covers ordinary cases; project-owned
   executable hooks and explicit properties handle complex ones. Do not make a
   proprietary test DSL the only route to advanced behaviour.
6. **Prefer contracts and honest measurements.** Specifications define the intended
   boundary. Inference helps draft missing contracts but cannot prove its own
   coverage. Unknown and unsupported cases remain visible.
7. **Automate cases, not the meaning of correctness.** Generate from specifications
   and declared properties; reuse existing assertions. A recorded response is an
   observation, not automatically the required response.
8. **Make each adopter useful to the next.** A provider's evidence improves its
   consumers' tests; consumer assumptions identify valuable provider checks.
   Participation is incremental and sharing is under each team's control.
9. **Leave teams free to change technology.** Protocol support and execution
   adapters must not force an application SDK, programming language or framework.
   Portable evidence and reproducible cases must survive a tool migration.

## Product and business model

These are proposed product boundaries, not currently available plans or prices.

| Offering | What users receive | Commercial role |
| --- | --- | --- |
| **Free open local engine** | Capture, validation, OKF, comparison, verification, exploration and offline reporting as those capabilities ship. Works with public or private projects, local files and compatible artifact stores. | Individual adoption, trust and an open ecosystem. No account or subscription needed for local use. |
| **Free public registry** | Publish, discover, browse and pull openly licensed bundles for open-source APIs; release history, provenance and public verification evidence. | Reusable provider knowledge, examples and discovery that benefit maintainers and consumers. Operates within published usage limits. |
| **Paid private registries** | Managed organization namespaces, private catalogues and dependency graphs, team access, retention, audit history, ownership, policies and verification coordination. | Recurring revenue for operating API assurance across teams. Customers can consume public bundles while keeping their own evidence private. |
| **Enterprise options, after validation** | Organization-wide identity integration, advanced governance, support commitments and potentially dedicated or self-hosted deployments. | Meet demonstrated procurement and deployment needs without building every hosting model at launch. |

Payment is for the managed private service. Private local use, private comparison
and execution on a company's own infrastructure remain free. The hosted product
uses the same verdicts and evidence formats as the CLI. Customers can export
bundles, dependency mappings, policies and verification results, mirror artifacts,
and reproduce supported analyses locally. Server-code licensing is a separate
decision from the open engine and public formats, to settle before distribution.

The paid value must exceed storage: companies already have artifact stores.
Sell the ability to discover affected teams, resolve assumptions, coordinate
checks and explain release readiness with durable evidence. Basic access control,
tenant isolation and protected transport/storage belong in every private plan.

Start commercial validation with an organization subscription and included
storage/transfer/coordination allowances. Test service-count bands only if buyers
find them predictable. Include ordinary contributors and CI identities; avoid
per-test, per-condition or per-dependency-edge charges that discourage useful
evidence and network growth. Extra retention, transfer or hosted compute can have
explicit budgets. Set prices after pilots establish willingness to pay and cost
to serve; do not promise unlimited storage or execution.

There is precedent for public/private registry pricing in
[npm](https://docs.npmjs.com/about-private-packages/) and
[GitHub Packages](https://docs.github.com/en/billing/concepts/product-billing/github-packages),
and for paid managed contract collaboration in
[PactFlow](https://pactflow.io/pricing/). These are precedents for the packaging;
demand for Wiretap still needs customer evidence.

## What exists today

Wiretap already provides:

- A local binary, HTTP control interface, CLI and thin Go/JavaScript lifecycle
  integrations for existing tests.
- HTTP/OpenAPI and native unary gRPC/Protobuf capture, validation and bounded
  contract-condition coverage. gRPC uses reflection by default, with local
  contracts as an alternative.
- OKF bundles containing authoritative JSON evidence, frozen contracts and
  payloads, with derived Markdown, an offline HTML viewer and a knowledge index.
- Distinct provider observations and dependency assumptions, source provenance,
  evidence limitations and a suggested verification backlog.
- HTTP provider invalid-input exploration from a passing captured scenario,
  with external hooks for fixtures, authentication, cleanup and assertions.

Cross-bundle comparison, provider verification of consumer scenarios, recorded
dependency simulation, general stateful exploration, automatic work selection,
registry services and the connected web runner are still to be built. Current
exploration does not capture or replay downstream dependencies. gRPC exploration
and streaming coverage are not available.

The [architecture](architecture.md), [coverage rules](contract-coverage-rules.md),
[bundle knowledge](bundle-knowledge.md) and [gRPC plan](grpc-support-plan.md)
remain the detailed references. This roadmap does not mark their future features
as implemented.

## One feedback loop, from one team to many

### Value on either side of an API

Wiretap is useful to systems that provide APIs, consume APIs, or do both. A
system does not need to sit between a test client and downstream dependencies
to benefit. These roles describe API boundaries, not whether an application has
internal storage, a browser interface or other implementation details.

| Application role | Value proposition | Useful evidence |
| --- | --- | --- |
| **Provider only:** a service with no outbound API dependencies | Know what the API promises, what tests exercised, and where further verification is needed. | Contract conformance, operation/condition coverage, provider test scenarios and generated rejection results. Publish evidence for future consumers without waiting for them to adopt Wiretap. |
| **Consumer only:** a UI or client that exposes no API | Know whether it works against what its dependencies can actually return. | Captured API requests, mocked-response assumptions, named test outcomes, dependency contract conformance and gaps requiring provider evidence or consumer variation checks. |
| **Provider and consumer:** a service calling other APIs | Verify both its promises to callers and its assumptions about dependencies. | Linked inbound/outbound observations, with each boundary's coverage, assumptions and provenance kept distinct. |

For a provider-only service, start with its existing API tests: validate responses,
show untested operations and conditions, and use the existing HTTP invalid-input
explorer where applicable. Broader valid-boundary and property exploration follows
the roadmap. The team gets value before publishing a bundle or involving another
team; sharing later makes that evidence useful to its consumers.

For a consumer-only UI, the intended workflow is to route its API calls through
Wiretap while its existing UI test framework owns execution and assertions.
Capture the requests and dependency responses, including mocks, and check them
against the dependency contracts. Future cross-bundle comparison verifies the
assumptions against provider evidence; dependency variation reruns those same
tests against other permitted responses, documented errors or injected faults.

For example, a UI's mock may always return a populated list with every optional
field present. A variation can return an empty list or omit a permitted optional
field, exposing a rendering failure through the UI's existing assertions. Wiretap
records the relevant dependency behaviour and outcome; it does not infer that
the test checked every displayed field.

The first-class consumer-only capture path, cross-bundle comparison and dependency
variation remain planned work. They need a working example without a dummy
provider API or inbound request. API-boundary evidence does not measure visual,
accessibility or complete user-journey coverage; those remain responsibilities
of the existing test tools. A system with neither provided nor consumed APIs has
little API-assurance value to gain from Wiretap.

Consequently, `provides` and `consumes` are independently optional in the planned
configuration. Either may be omitted or empty. An absent side is not a reason to
invent an API, and an empty inventory must never become a claim of full coverage.
See the [contract package plan](contract-package-plan.md) for runtime and
acceptance requirements.

### The shared feedback loop

```text
Existing tests and mocks
          |
          v
Capture API behaviour, assumptions and coverage into OKF
          |
          v
Compare with contracts, provider evidence and previous versions
          |
          v
Select an unverified assumption, meaningful change or coverage gap
          |
          v
Verify the provider or vary a dependency and rerun the consumer
          |
          v
Preserve evidence and a reproducible regression case in a new bundle
          |
          +----> Reuse across teams and repeat
```

For example, Checkout mocks Payments returning an optional `receipt_url` on every
successful charge. Wiretap can immediately say that Checkout tests observed the
field; it cannot infer that Checkout requires it. The provider contract permits
omission, but provider tests may not demonstrate that case yet.

Wiretap should generate two useful checks: rerun Checkout's existing test with
the field omitted, and give Payments a verification task for the relevant
scenario. If Checkout fails, save the dependency variant and failure as a
regression case. If Payments verifies the scenario, publish the exact build,
expectations and result. Other consumers can reuse that evidence and test the
same permitted behaviour without rediscovering the issue.

Permitting omission does not require Payments to produce it in every scenario,
or even establish that this version has a reachable state that produces it.
An undemonstrated permitted outcome remains an evidence gap, not a provider defect.

This loop works before every team adopts Wiretap. One team gets coverage and
regression evidence; two teams can verify their agreement; subsequent adopters
reuse examples and expose more valuable gaps.

## Delivery sequence

Build **evidence and agreement** and **execution and search** together. Add an
optional **registry and commercial service** track once artifact identities and
comparison semantics are stable. Ship narrow complete loops before expanding
any track into a large platform.

| Phase | User outcome | Release gate |
| --- | --- | --- |
| 1. Find incorrect assumptions | Compare consumer and provider evidence locally and explain meaningful changes. | Independent repositories produce correct, version-specific findings and actionable unknowns. |
| 2. Close the verification loop | Execute a provider check or dependency variation and preserve the result. | A reported gap becomes a reproducible check and a new evidence bundle. |
| 3. Multiply the value of each test | Explore valid boundaries, combinations, properties and faults from a few flows. | Known defects are found and reduced under explicit time and case budgets. |
| 4. Make evidence compound | Share results, select affected checks and coordinate verification across repositories, optionally through the registry. | A change triggers the right checks in participating projects; exported inputs support the same analysis without the service. |
| 5. Cover more real system boundaries | Extend the same semantics to broader contracts, streaming and asynchronous APIs. | Every supported transport passes published capture, execution and evidence conformance tests. |

The registry track should reach a public pilot and a paid private pilot alongside
Phases 1–2. It must not wait for every exploration algorithm or for Phase 4 to be
complete. Its later automation depends on the corresponding local capability:

| Registry increment | Dependency | Release gate |
| --- | --- | --- |
| **R1. Publish, pull and public catalogue** | Stable bundle/package identities and a portable exchange client. | An independent maintainer publishes release evidence and an unrelated consumer reuses it. Digest-pinned round trips through independent compatible registries and offline reads work. |
| **R2. Managed private pilot** | R1, local comparison and the thin provider-check loop. | Two teams resolve a real assumption inside one private organization; public evidence can be used without revealing private relationships; tenant-isolation, restore and export checks pass. Export reproduces local analysis and a design partner validates paid value. |
| **R3. Coordinated verification and PR assistance** | Reliable Phase 2 execution and Phase 4 impact analysis. | One update runs relevant checks in two opted-in repositories, publishes results and produces deduplicated, evidence-linked draft PRs. |
| **R4. Interactive web execution** | Stable execution profiles and connected runners from Phase 2. | A selected scenario runs through UI and CLI with equivalent verdicts, fresh evidence and correct cancellation/cleanup. Manual observations remain distinct from asserted checks. |

R3 and R4 can proceed independently once their execution prerequisites work.
The interactive runner does not need to wait for automated PR assistance.

### Phase 1: find incorrect and unsupported assumptions

Implement a local comparator that accepts explicitly selected consumer/provider
bundles and a project-owned mapping of API identities and versions. Compare
consumer requests with the provider contract, mocked responses with permitted
provider responses, and observed conditions with provider-test evidence.
Comparison is directional: a request the consumer emits and a response the
consumer accepts have different compatibility rules.

Report contradictions, supporting examples and missing evidence separately.
Matching hashes or condition keys identify evidence to examine; they are not
compatibility verdicts. Different contract revisions need explicit semantic
comparison, with unsupported constructs producing an unknown result.
Represent proposed, fake-first assumptions from the first release, even when
there is no provider implementation yet.

Behavioural disagreement requires comparable scenario preconditions: fixture
state, identity/role, request meaning and expectations. A provider's 404 and a
mock's 200 can both be correct for different state. When equivalence cannot be
established, generate a verification task rather than declaring a contradiction.

Add baseline-versus-change bundle comparison for both inbound results and
outbound behaviour. A test can still return HTTP 200 while charging twice,
sending the wrong currency or omitting a dependency call. Explain these changes
with evidence links. Use explicit normalization rules for dynamic values and
only assert ordering where the scenario or causal evidence supports it.

Add a declared complete API inventory so absent operations and entirely untested
registered services are visible. Without that declaration, report coverage only
over known scope. Keep inferred mock specs outside coverage denominators.

Make `.wiretap.yaml` the declaration of application name, optional stable ID,
description, provided APIs/specs and consumed APIs/specs. Keep consumer aliases
separate from provider identity and runtime targets. Define spec releases,
locked source revisions and consumer-owned derivatives independently of bundles,
following the [contract package plan](contract-package-plan.md).
Support provider-only, consumer-only and mixed declarations. Deliver a
consumer-only capture example with no SUT API binding, using the existing test
lifecycle and dependency routes, before calling that adoption path supported.

Expose the findings as JSON, readable OKF pages, an offline view and configurable
CI outcomes. Begin with advisory unknowns; allow teams to prevent regressions in
previously verified relationships without blocking adoption on every old gap.

**Done when:** a two-repository example distinguishes an actual contract
contradiction, a supported scenario and an unverified assumption; flags a changed
outbound call despite an unchanged successful response; and cannot pass using a
stale or incorrectly mapped provider version. Include a thin provider-check path
using existing hooks so one finding can be resolved end to end.

### Phase 2: turn assumptions into executable verification

Build provider verification from selected consumer scenarios. The provider
project supplies its target, fixture setup, fresh authentication, bindings and
business assertions through the existing language-neutral hook mechanism.
Expectations must be explicit: contract conformance, a declared property, or a
reviewed response matcher. Do not silently promote every recorded value into a
requirement.

Add optional bundle-backed dependency scenarios so a consumer can rerun its
existing tests with recorded or deliberately varied provider behaviour. Keep
existing mocks supported. Offer precise matching, per-test state and sequence
control, response-to-request bindings, and diagnostics explaining mismatches.
Unexpected or ambiguous calls fail visibly by default; any permitted passthrough
is explicit and recorded. A closest-looking match is a suggestion, never verified
evidence that the right scenario ran.

Support valid alternative responses and documented errors first, followed by
bounded timeouts, resets and retry sequences. Invalid dependency payloads are
optional resilience tests with separate reporting; they do not become required
mock contract-coverage targets.

Keep bundles immutable. Execution configuration, hook code, credentials and
fixture policy stay in the consuming project. Store derived scenario definitions,
selection rules and lineage without embedding arbitrary executable hooks.

Ship this phase in three increments: one HTTP provider-verification loop; one
consumer dependency-variation loop using an existing test; then multi-step,
parallel-isolation and unary gRPC execution. Each increment should be usable
before the entire matrix is complete.

**Done when:** fresh-state multi-step HTTP and unary gRPC reference scenarios can
verify a provider and exercise a consumer dependency variant. Authentication
refresh, ID binding, cleanup and isolated workers work reliably. Missing fixtures,
redacted inputs and ambiguous matching are explicit blockers, not passes. A
failure reproduces from a clean start with its execution prerequisites recorded.
This adds targeted unary execution; schema-driven gRPC exploration remains later
work.

### Phase 3: generate useful tests and smaller failures

Expand today's deterministic invalid-input checks into targeted valid boundary
generation, feasible combinations, property checks and stateful sequences.
Prioritize changed contracts, consumer demand, uncovered conditions and previous
failures. Preserve predictable finite checks alongside optional search engines.

Let teams declare properties once and apply them to many cases: rejected requests
leave state unchanged, retrying an idempotent operation creates one effect,
read-after-write returns the created value, or pagination preserves the intended
set. These properties require explicit domain meaning and observable evidence;
Wiretap must not infer them from endpoint names.

Use counterexample shrinking to remove irrelevant values and sequence steps while
preserving the same defect. Every attempt must reset fixtures and refresh auth.
A validation failure must not shrink into an unrelated 401 or missing resource.

Add assertion-sensitivity checks: vary meaningful behaviour and see whether the
existing test detects it. A surviving change is a possible assertion blind spot,
not automatically a bug. Keep equivalent and indeterminate mutations out of
claims about detection effectiveness. Require a fresh passing baseline, evidence
that the mutation was applied and reached, and an identified assertion result.
Setup, mock-matching and protocol failures do not count as assertion detections.

**Done when:** a reference suite with seeded validation, optional-field, retry and
side-effect defects finds the intended failures, records the property actually
checked, and produces smaller cases that reproduce after a clean restart. Reports
retain the unattempted targets and budget limits. Demonstrate a reduction in
authored cases for the same declared assurance scope.

### Phase 4: compound evidence across teams and versions

Support both the Wiretap registry and existing Git releases, CI artifacts or
compatible registries. A project manifest maps dependencies to API identities,
contract/build revisions and bundle digests. Discovery may suggest a newer bundle;
verification decisions use pinned inputs. A provider publication does not
automatically upgrade the consumer's application dependency.

Build a rebuildable multi-bundle index, usable locally and in the service, with
incoming assumptions, provider support, ownership and unresolved work. Graph
edges come from explicit API mappings and recorded calls, not download counts.
Distinguish declared/proposed dependencies, observed use and scenario verification
against a particular provider build. A service-level summary must expose the
operation and condition gaps underneath it.

Use changes and evidence lineage to select affected checks. A new provider version
invalidates or rechecks relevant claims; it does not inherit assurance because its
contract filename is unchanged. Unknown impact falls back to broader execution.
Keep a full-run option and a visible selection manifest.

Allow a target-version manifest to answer whether the specific intended set of
services has sufficient evidence to change safely under project policy. Without
that inventory, report compatibility of the supplied versions only; do not infer
what is deployed.

Add opt-in subscriptions that turn new provider or consumer evidence into bounded
verification jobs. Dispatch them to an authorized project runner or CI system;
publish results with exact input identities. Deduplicate jobs and findings across
retries, and prevent cycles in the dependency graph from triggering endless work.

PR assistance starts with reproducible checks and evidence: a missing provider
test, a consumer regression case, or a proposed fixture/binding change. Add
suggested implementation repairs later. Each repository controls its automation;
changed PR heads invalidate outdated checks. Keep automatic merging outside the
initial scope, and never weaken expectations or rewrite mocks merely to obtain a
pass. Private findings must not leak into public upstream PRs.

Expose query, selection and execution interfaces, then a thin optional MCP
adapter. Agents follow evidence to a bounded task and produce a new bundle.
Core verdicts work without an LLM; payloads and specs remain untrusted data.

**Done when:** a provider change generates checks for two independently maintained
consumers, their results can be assembled locally or through the registry, and
new evidence resolves or reopens the correct tasks. Copies and derived reports
do not count as independent corroboration. A third consumer can reuse the
resulting examples and checks; duplicate events do not produce duplicate PRs.

### Phase 5: extend coverage without fragmenting the product

Close the documented unary gRPC interoperability and rich-error gaps, then add
streaming capture, execution and coverage with explicit message and lifecycle
semantics. Extend exploration to Protobuf constraints that can actually be
evaluated; do not invent error-code or validation requirements from structural
types alone.

Broaden OpenAPI/JSON Schema support, starting with an explicit supported-dialect
matrix and OpenAPI 3.1. Add AsyncAPI/message boundaries with correlation,
acknowledgement, ordering, duplication and delivery-failure semantics. Prioritize
specific transports from adopter demand, followed by other API forms such as
GraphQL or WebSockets where the same evidence loop is valuable.

Publish a protocol-adapter contract and conformance fixtures after at least two
implementations reveal stable abstractions. Preserve protocol-specific meaning
instead of reducing every interaction to HTTP-style request/response fields.

**Done when:** each advertised capability has provider, consumer and mixed-system
examples; round-trippable portable evidence; truthful coverage limits; and local
CI execution. A new transport can be added without replacing users' test
frameworks or changing the meaning of earlier results.

Small gRPC completion work and schema fixes should ship earlier where useful.
Broadening the protocol list must not delay the first complete assurance loop.

## Registry and interactive workspace design

### Application declarations and spec packages

The [contract package plan](contract-package-plan.md) defines the proposed YAML
and acceptance cases. Providers declare their application and provided spec
sources; consumers declare upstream APIs under convenient local aliases. Both
sides support local files, remote URLs and registry references. Spec discovery
and declaration do not imply that an API was exercised or verified.

Version specs independently from application builds and evidence bundles. A
human-friendly spec version resolves to exact frozen content; each test run
records its build and actual spec revisions. Repeating tests or rebuilding a
viewer requires no manual spec or bundle release. Standalone spec publication
supports providers that do not yet have test evidence, while complete OKF bundles
remain self-contained.

Consumers can name and version modified specs, including codegen adjustments,
with explicit lineage to the exact original. Keep upstream and derived content
separate, pin both, and never infer compatibility from a version label or
`derived_from` relationship. A codegen variant does not silently replace provider
validation; meaningful wire changes become visible assumptions to verify.

Add explicit resolution/update and a generated lockfile so remote sources and
variant bases remain reproducible. Preserve the gRPC reflection default as a
contract acquisition method, with descriptors frozen per run. Declarations,
aliases and sources remain usable without a Wiretap registry account.

### Distribution, analysis and execution

Keep storage, analysis and execution separate:

| Component | Responsibility |
| --- | --- |
| Registry | Immutable package distribution, namespaces, provenance, release references, discovery and access control. |
| Evidence index and coordinator | Dependency/verification views, comparison, subscriptions, work routing and result history, using the same analysis engine as the CLI. |
| Project-owned runner | Network calls, fixtures, authentication, hooks, assertions, cancellation and cleanup. Runs on a developer machine or customer-controlled CI worker. |
| Web workspace | Browse evidence, inspect the graph, select scenarios or variations, choose a configured target and request execution. |

Use OCI-compatible distribution for the initial packaging design, subject to an
interoperability spike. OKF remains the content format. OCI already supports
non-container artifacts and associations useful for provenance or result
attachments; a new proprietary storage protocol is unnecessary. Define the
Wiretap artifact profile and demonstrate transport through two independent
registries. See [OCI artifact support](https://opencontainers.org/posts/blog/2024-03-13-image-and-distribution-1-1/).

Keep API ownership, contract revision, application build, run digest and release
label distinct. Many runs can support one software release; publishing another
run is not publishing a new application version. Release references select
evidence without merging results across incompatible builds or profiles.
Friendly tags aid discovery; comparisons and executions resolve exact digests.
Track the OCI package digest separately from authoritative evidence identity:
recompression or rebuilding HTML can change packaging without creating another
observation. Verify transport integrity and preserve the underlying run/snapshot
lineage so republishing cannot inflate independent evidence.
Separate verification artifacts record their inputs, expectations, execution
context and result. Verified publisher identity establishes origin, not that a
scenario or implementation is correct. Distinguish maintainer-published evidence
from community captures and retain missing or incomplete build provenance.

The web runner should offer a Postman-like interaction over existing evidence:
inspect a flow, select or edit a request, choose a scenario/property and target,
then inspect the new result. Use a paired local runner or an authorized CI worker
through the same execution interface as the CLI. Some private HTTP targets may be
browser-accessible, but the full workflow needs a runner for native gRPC, project
hooks, fixtures and targets beyond the browser's permitted network access.
Postman also uses agents for requests beyond browser capabilities; see its
[agent architecture](https://learning.postman.com/v11/docs/getting-started/basics/about-postman-agent).

Execution profiles, permitted targets, hook code and credentials stay in the
project. Bind each runner connection to an authenticated session and allowed
project scope. Viewing or pulling a bundle never executes commands or sends API
requests. User edits produce new scenario/result artifacts with lineage, never
rewrite captured evidence. An interactive request without assertions is an
observation, not a passing test. Retain the standalone offline viewer.

### Public and private publication boundaries

Public source code does not make every captured payload suitable for publication.
Require explicit destination/visibility policy, publisher namespace ownership,
redistribution terms for bundled content and a reviewable publication preview.
Prefer sanitized fixture-based captures; secret scanning helps but cannot certify
that arbitrary payloads are safe. Sanitization creates a new artifact with stated
evidence/replay limits. Do not host an uploaded bundle's executable HTML on the
registry origin; render validated evidence with trusted viewer code.

Private access rules cover payloads, search, graphs, derived findings, job logs
and PR content. A private consumer can use public provider evidence without
publishing its identity, requests or dependency edges. Results involving private
inputs remain private unless deliberately prepared for publication. No automatic
fallback from a private package namespace to a same-named public package.

Publish quotas for bundle size, storage, transfer and indexing work. Use bounded
parsing, rate limits and content reuse without exposing private artifact
existence across tenants. Free public hosting does not include unlimited test
execution; customer-owned runners are the initial model. Hosted execution, if
introduced, needs a separate isolation and cost model.

Document retention, withdrawal, compromise and secret-removal procedures. Content
is never silently replaced under an existing digest, but immutability does not
promise indefinite hosting. Withdrawn or unavailable inputs remain explicit in
dependent results; authorized consumers can retain pinned copies for repeatable
analysis. Full export and a tested migration path are release requirements.

## The techniques behind fewer hand-written cases

| Technique | Value | Measurement boundary |
| --- | --- | --- |
| Schema partitioning and boundary values | Exercise enums, optionality, branches, lengths and numeric edges systematically. | A finite catalogue of classes, not every possible payload. Negative witnesses isolate an intended violation. |
| Feasible pairwise and selected higher-order combinations | Find interacting conditions without an exhaustive cross-product. | Declare combination strength and scope; distinguish proven infeasible, unsupported and unattempted combinations. |
| Property and metamorphic checks | Apply one meaningful rule across many inputs and related executions. | Record the rule and whether its prerequisites and assertion were reached. |
| Stateful sequence generation | Explore operation relationships, resource lifecycles, retries and pagination. | Use declared preconditions, bindings and resource pools; require reliable state reset. |
| Controlled dependency faults and variations | Find brittle consumers and incorrect error handling. | Record exactly what changed and what externally observable behaviour was checked. |
| Feedback-guided search and shrinking | Spend budget on useful gaps and produce smaller reproductions. | Preserve seeds, engine versions, concrete cases, failure identity and fixture prerequisites. |
| Assertion-sensitivity analysis | Reveal cases where tests exercise behaviour but fail to check it. | Report meaningful, equivalent and inconclusive mutations separately. |
| Corpus minimization and change-impact selection | Run fewer cases while retaining selected evidence contributions. | Publish a selection manifest; preserve original cases and a full-run path. Equal coverage does not imply equal business meaning. |

Contract conditions, combinations, properties and sensitivity are separate
measurements. Optional application code-coverage signals can help search and
selection later, but must not become an adoption requirement or a substitute for
boundary evidence.

## Assurance must remain explainable

Extend the existing [coverage rules](contract-coverage-rules.md) rather than
introducing a single aggregate “integration confidence” score.

| Question | Evidence required |
| --- | --- |
| Are all intended APIs represented? | A declared inventory and explicit exclusions. Traffic alone is insufficient. |
| Did messages conform to the contract? | Actual messages evaluated against a frozen supported contract. |
| Which contract cases were exercised? | Conditions observed together in complete eligible executions, under a named measurement profile. |
| Does the provider support this assumption? | Clearly distinguished contract permission, provider-test examples or direct scenario verification against an identified build. |
| Does the consumer tolerate this behaviour? | Its test or declared property executed against the dependency variant, with its result. |
| Would the tests notice an incorrect behaviour? | A meaningful controlled mutation and evidence that an assertion detected it. |
| Is the result relevant to this change? | Exact source/build, contract and evidence identities, plus the selected target versions and scope. |

These are bounded claims. An unobserved provider response is not a contradiction;
a schema-valid response is not proof of consumer safety; a changed response is
not automatically a regression. Authentication/setup failures are not successful
validation tests. Passing tests do not prove assertions about every captured
field. Keep failed, incomplete, unsupported, stale and unknown evidence visible.

A bundle comparison or verification produces its own result artifact referencing
the exact input digests, expectations, configuration and algorithm versions.
It does not rewrite its input bundles or inherit their coverage as newly executed
coverage. Hash integrity identifies content; trusted CI provenance or optional
attestation is needed when who produced it matters.

## How the network effect works

There are two connected networks. The public registry accumulates reusable
open-source provider knowledge and attracts adopters. Private registries connect
internal teams, their dependencies and selected public evidence, creating ongoing
organizational value. Neither requires companies to publish internal evidence.

| Contribution | Immediate benefit to the contributor | Benefit to other teams |
| --- | --- | --- |
| Provider tests and contract | Visible boundary coverage and regression evidence. | Consumers can select realistic, versioned examples. |
| Consumer tests and mocks | Unverified assumptions become visible. | Providers learn which scenarios consumers actually exercise. |
| Provider verification | A concrete assumption is checked against the implementation. | Participating consumers can reuse the result for the same relevant scope. |
| Consumer variation result | Brittle handling and assertion gaps are found. | Other consumers can try the same permitted case. |
| Minimized failure and repaired regression | A cheap, reproducible guard against recurrence. | Reusable scenarios and stronger verification for the whole dependency graph. |

Start with local files and manual artifact selection, then make reuse easy through
publish/pull and an early registry browser. Automate acquisition and CI handoffs
once comparisons and execution are reliable. A single project still benefits;
adoption needs neither a company-wide catalogue nor simultaneous team migration.

Sharing policy matters: select boundaries, remove secrets, and publish only the
evidence permitted for that audience. Redaction can limit verification or replay;
report that limit instead of treating sanitized placeholders as real values.
Executable hooks, credentials and private fixture logic stay with the project.

The network becomes more useful as it gains independent scenarios and verified
relationships, not merely more bundles. Track demand and evidence lineage so
duplicate exports, repeated passing samples and circular references cannot inflate
assurance. Freshness is relevance to a build and contract, not just recent time.

## Architecture and reuse

Keep a small set of clear boundaries: contract/evidence readers, candidate
generation, protocol execution, fixture/property hooks, verdicts, and report/query
adapters. Customer languages integrate through existing tests and external
commands. Avoid maintaining an application instrumentation SDK for every language
or building a universal plugin framework before extension points are proven.

Evaluate Hegel early as an optional search/shrinking engine. Its current design
uses Rust `libhegel` with language bindings, rather than the older Python-server
architecture. Wiretap should own contract translation, transport, fixture
lifecycle, properties, coverage and OKF evidence. Hegel can supply search
machinery. Its beta stability, packaging, supported platforms and structured
result access need a bounded feasibility spike before adoption.
Check the current Go binding's Go 1.26 requirement against Wiretap's Go 1.24
baseline, native-library extraction/loading, and access to failures without
parsing console output.
See [Hegel architecture](https://hegel.dev/explanation/how-hegel-works),
[compatibility](https://hegel.dev/compatibility) and the
[Go implementation](https://github.com/hegeldev/hegel-go).

Store concrete minimized scenarios alongside engine-specific reproduction data
so artifacts remain useful when an engine changes. Keep existing deterministic
invalid-input generation usable independently. Apply the same build-or-reuse
test to schema compatibility and protocol libraries: reuse mature machinery,
retain open interfaces and control Wiretap's evidence semantics.

## What we should absorb from the alternatives

The target is one coherent API workflow covering the reasons teams adopt these
tools. This is not a requirement to reproduce every platform feature.

| Reference | Capability Wiretap should offer or integrate | Product emphasis |
| --- | --- | --- |
| Pact, PactFlow and Drift | Directional consumer/provider agreement, explicit matchers, provider verification and version-aware change decisions. | Reuse existing tests and distinguish declared compatibility from actual provider evidence. See [matching](https://docs.pact.io/getting_started/matching), [version verification](https://docs.pact.io/pact_broker/can_i_deploy) and [Drift's scope](https://pactflow.github.io/drift-docs/docs/concepts/where-drift-fits/). |
| Speedscale ProxyMock | Recorded dependency scenarios, replay, binding/matching diagnostics and promoting useful traffic into tests. | Optional simulation behind existing tests, with explainable strict matching. See [architecture](https://docs.speedscale.com/proxymock/how-it-works/architecture/) and [match diagnostics](https://docs.speedscale.com/proxymock/guides/mock-match-rate/). |
| Keploy | Low-effort capture/replay, integration with existing tests, parameterization and useful corpus selection. | Portable API evidence and gradual adoption; broad database wire emulation is a separate investment. See [existing-test mocking](https://keploy.io/docs/running-keploy/mock-your-tests/) and [parameterization](https://keploy.io/docs/running-keploy/keploy-templatize/). |
| HyperTest | Regression analysis of outgoing interactions as well as incoming responses. | Local bundle comparison catches changed dependency behaviour even when the public response is unchanged. See [approach](https://www.hypertest.co/detailed-write-up) and [architecture](https://docs-v2.hypertest.co/overview/how-it-works). |
| Antithesis | Properties, targeted fault exploration, assertion reachability and useful reproductions. | Apply these at observable API boundaries. Whole-environment deterministic execution requires infrastructure beyond a proxy. Specifications, local execution and AI-generated tests alone are not distinctive.
The defensible advantage is the compounding loop between provider evidence,
consumer assumptions, targeted execution and portable knowledge. The
[Pact roadmap](https://docs.pact.io/roadmap) and
[September 2026 update](https://docs.pact.io/blog/2026/09/14/pact-open-source-update-sept-2026)
also show why a competitor checklist would quickly become stale.

## Adoption, distribution and success measures

Make the first experience small: add Wiretap to one existing suite, retain one
bundle, see a useful coverage gap or dependency assumption. Adding comparison
should require a second artifact, not replacing the test suite. Advanced execution
can require fixtures, reset capability and properties, but those requirements
must be explicit and scoped to that capability.

Alongside Phase 1, choose and publish an open-source license and contribution
policy; produce reproducible binary/container releases; document the format and
support matrix; and ship a compact two-repository demo with known integration
defects. Licensing is a prerequisite for the public open-source release. Keep
the CLI, machine interfaces, examples and offline viewer aligned.

Seed the public registry with maintained HTTP and gRPC reference projects and a
short publish/consume example. Work with maintainers to publish useful release
evidence with clear ownership and licensing. Target private pilots at companies
with multiple teams already developing against mocks; use the local comparison
to demonstrate a real assumption gap before selling organizational rollout.

Use pilot projects to set targets and publish results with their methodology:

- Time to the first useful bundle and first verified assumption; required test,
  application and hook changes.
- Share of dependency relationships with relevant version-specific provider
  evidence; age and cause of unresolved assumptions.
- Actionable findings versus false positives, and the fraction blocked by setup,
  incomplete capture or unsupported semantics.
- Meaningful new defects found per exploration minute and authored property.
- Reproduction success after a clean reset, and reduction in failing-case size.
- Execution time and authored cases needed for the same declared assurance scope.
- Reused provider scenarios, independently verified relationships and cross-team
  verification tasks closed.
- Public activation: independent maintainers publishing useful evidence and
  unrelated consumers reusing it; freshness and cost per usefully reused bundle.
- Private activation and expansion: time to a verified relationship across two
  teams, subsequent teams onboarded, paid conversion and renewal based on value.
- Service economics: retained bytes, transfer, indexing/coordination work,
  support effort and gross margin per active organization. Keep publishing
  volume separate from demonstrated customer value.

Test counts, generated payload counts, a blended coverage percentage and number
of AI interactions are not success measures. The goal is earlier trustworthy
feedback with less authoring and less infrastructure.

Before the first external public pilot, verify publisher ownership, safe handling
and rendering of malformed uploads, publication visibility and bounded usage.
Before the first private pilot, demonstrate tenant isolation across blobs and
derived data, private consumption of public evidence, backup/restore and export.
Before enabling connected execution, test scoped runner authorization, cancellation
and cleanup. Access revocation must control subsequent hosted access and runner
credentials; it cannot retract artifacts already exported or cached.

General availability additionally requires a sustainable free-public operating
budget and support/operating procedures demonstrated through pilots. Dedicated
hosting, a self-hosted server offering and Wiretap-hosted execution each require
separate demand and operating-cost validation.

## First implementation handoff

The next detailed plan should deliver the Phase 1 loop in small reviewable pieces:

1. Define explicit API/version mappings, comparison findings, evidence references
   and CI policy semantics; reuse current identities and measurement profiles.
   Implement the application/provided/consumed declaration and identity model in
   the [contract package plan](contract-package-plan.md).
2. Create independently captured provider and consumer fixtures covering agreement,
   contradiction, proposed assumptions, missing evidence, non-comparable setup,
   stale versions and incomplete payloads.
3. Implement directional contract/evidence comparison with conservative unknowns
   for unsupported semantics, then outbound-aware baseline comparison.
4. Produce portable result artifacts and readable explanations over the same
   machine-readable findings; add complete API inventory declarations.
5. Resolve one selected finding through a provider check using existing hooks,
   fresh fixtures and explicit expectations; link its new evidence back to the
   original assumption.

Add a bounded registry design/spike alongside that implementation:

1. Specify package namespaces, visibility, release references, provenance and
   digest-pinned dependency manifests without changing OKF's evidence semantics.
   Include independent spec publication, local/remote source locking and
   consumer-variant lineage, with explicit rebase semantics.
2. Prove publish/pull, integrity verification and offline use through two
   independent OCI registries; use a trusted renderer for the browser prototype.
3. Define public quotas/retention and private tenant boundaries; test a private
   consumer of a public provider before building broad search or automation.
4. Recruit an open-source maintainer and a two-team private design partner; test
   useful reuse, willingness to pay and a complete export path.

Run the bounded Hegel feasibility spike and finish small unary gRPC gaps as
capacity permits. Defer broad protocol expansion, generalized simulation,
hosted execution and richer search until the initial comparison-to-verification
loop is trustworthy. Registry design can proceed early; commercial coordination
must build on working local capabilities.
